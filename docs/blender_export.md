# Blender export

The app can export the current octree to a self-contained `.glb` plus a Blender
setup script that reproduces the Vulkan renderer's material blending. This
document describes the workflow, the implementation and the known limitations.

## Workflow

1. In the running app choose **File -> Export to Blender (.blend)...** (or
   press **Export to Blender (.blend)** in the *Octree Explorer* widget). Pick
   an output path; `.blend` is appended automatically if missing.
2. The export runs on a background thread (progress window, cancellable).
   Brush edits wait for it because the exporter holds each layer's shared lock.
3. The exporter writes the interchange files and then runs **Blender
   headlessly** to build and save the scene:

   | File | Contents |
   |------|----------|
   | `<name>.blend` | ready-to-render scene: imported mesh, blended materials, engine camera, sun, packed textures |
   | `<name>.glb` | tessellated octree mesh, embedded textures (intermediate; removed once the .blend exists) |
   | `<name>.octree.json` | material table, mixer definitions, camera/light/water/grass/SDF metadata, stats |
   | `<name>_blender.py` | Blender 4.x importer + material builder |
   | `<name>_blender.log` | headless Blender output of the `.blend` step |
   | `<name>_README.txt` | short usage note |
   | `<name>_tiles/` | UDIM texture tiles, written by the Blender script (not needed after packing) |

4. Open the `.blend` in Blender 4.x — it already has the camera, sun, world and
   materials configured and renders as-is (the textures are packed, so the
   scene is self-contained). To re-run the setup from the source data:

   ```sh
   blender --background --python <name>_blender.py -- <name>.octree.json \
           [--save-blend scene.blend] [--render out.png]
   ```

   or open `<name>_blender.py` in the *Scripting* workspace and press
   **Run Script** (with no argument it looks for the sidecar next to it).

If Blender is not installed (or not on `PATH`), the `.blend` step is skipped
with a warning and the `.glb`, sidecar and setup script remain as a manual
route; set `BLENDER_EXECUTABLE=/path/to/blender` to point at a specific binary.

### Camera

The Blender scene gets a camera named `OctreeCamera`:

- exported from the app: the camera is placed at the engine camera's position
  looking at 2048 m ahead of it, with the engine's vertical FOV
  (`Camera::getFovYDegrees`), so the `.blend` opens on the same view you
  exported from;
- headless/server exports carry no camera, so the script auto-frames the
  terrain bounds instead.

Headless export (no GPU/display) is available for validation:

```
cd bin
./server --export-glb /tmp/octree.glb
```

This generates the procedural map, exports the terrain + water + grass (no SDF
effects, which live in the Vulkan renderer), and exits.

## Geometry extraction

The export uses the engine's own CPU walker
(`space/OctreeTriangleTessellator.cpp` + `space/Tesselator.cpp`) — the reference
implementation that the GPU topology pass mirrors. Every **chunk cell**
(`Octree::isChunkNode`) whose frontier rung is present (`chunkLod == 1`) is
tessellated exactly like the server's chunk meshes, including the
`finestSurfaceLod` fallback. No GPU readback is involved: the exporter
re-tessellates the SDFs on the CPU, which reproduces the GPU geometry (the
topology self-check in the renderer proves the two agree).

Notes:

- The walker deliberately emits shared-edge polygons from both adjacent cells
  for watertightness. The exporter removes exact duplicate triangles per chunk,
  which is why the exported triangle count equals the engine's unique triangle
  count.
- The walker emits the engine's Vulkan front-face order; glTF/Blender use CCW,
  so the last two indices are swapped during export.
- Engine coordinates are Y-up right-handed and are written to glTF as-is; the
  Blender importer bakes the Y-up -> Z-up conversion into the vertices. The
  material graph converts world positions/normals back to engine space for the
  triplanar math (`P_e = (x, z, -y)`) and converts the resulting world normal
  back to Blender space.
- Water is exported as the transparent layer's tessellated surface. Waves are
  generated by GPU tessellation shaders and are not reproduced; the Blender
  water material is a static, slightly transmissive sheet.

## Vertex attributes

| glTF attribute | Type | Meaning |
|---|---|---|
| `POSITION`, `NORMAL`, `TEXCOORD_0` | float | world-space mesh data (UVs are the CPU planar triplanar UVs) |
| `_OCTREE_MAT` (terrain) | vec4 float | `(texture index, hsv.x, hsv.y, hsv.z)` |
| `_VEG` (grass points) | vec4 float | `(variant, rotation fraction, height scale, 0)` |

The engine's per-vertex texture index is an `int`. Blender 4.0's glTF importer
aborts on integer custom attributes and also on mixing custom attributes with
different component counts, so the exporter packs the index and the HSV tint
into a single `vec4` FLOAT attribute per mesh (indices are small integers and
are exactly representable). The Blender script unpacks it.

Because glTF has no per-corner attributes, the script rebuilds the
tessellation-control/emission-shader behaviour on the imported mesh:

- per face it compresses the three corner texture indices into up to three
  unique slots (`u0`, `u1`, `u2`, first-seen order, `-1` dropped);
- it bakes one-hot per-corner weights, the flat face normal, and the
  per-face material parameters that differ between layers (triplanar scales in
  the default table) as **face-corner** attributes;
- Blender interpolates those corner attributes with barycentric weights, which
  is exactly what the TES does with `fragTexWeights`.

## Material blending (Blender node graph)

The terrain material is a port of:

- `SolidTesc.glsl` — slot compression and weights;
- `SolidTese.glsl` — interpolated weights, flat indices;
- `SolidSurface.glsl` / `Triplanar.glsl` — triplanar UVs, albedo/normal/
  roughness/AO blending, dominant-projection picks;
- `TangentBasis.glsl` — per-material normal conventions;
- `Hsv.glsl` — per-vertex HSV tint.

Reproduced equations:

- world-space triplanar UVs with the per-material `triplanarScaleU/V` and the
  shader's sign rules; per-layer tile selection via UDIM (`tile = 1001 + i%10 +
  10*(i/10)`);
- albedo: `sum_slot weight * sum_proj triW * albedo` (up to 3 materials, 3
  projections);
- normal: per-slot per-projection sample -> `applyNormalConvention` ->
  weighted projection blend -> `transformProjectionNormal` (the engine's
  world-space transform, ported with cross products) -> weighted slot blend;
  the final world-space normal is fed directly into the Principled BSDF
  (Cycles' Normal input is world-space, verified experimentally);
- roughness: dominant-projection sample, `mix(shininess, 1, rough *
  roughnessFactor)` blended across slots, then converted to a GGX roughness
  for the Principled BSDF (`alpha = sqrt(2/(p+2))`);
- AO: dominant-projection sample, `mix(1, ao, aoFactor)`, applied to the base
  colour (the engine applies AO to ambient light only — see limitations);
- HSV tint: the engine's hue rotate/saturation/value scaling applied to the
  base colour (Blender's HSV is 0..1; the engine's hue is degrees).

Texture colour spaces: albedo tiles are `sRGB`, normal/roughness/AO tiles are
`Non-Color`. The generated mixer layers (indices 21–25) have no source files;
the exporter bakes them on the CPU with the same two source layers and the same
equations as `TextureMixer.comp` (Perlin-scale/octave/contrast/brightness),
so they are included as ordinary tiles.

## Grass

The renderer's deterministic placement math was extracted to
`utils/GrassPlacement.cpp` (PRNG, hashes, biome noise, area-weighted slot
expansion, dominant-vertex brush test) and is shared by the renderer and the
exporter. The export writes the placed tufts as a point cloud; the Blender
script rebuilds the 12-blade tuft triangles with the vertex-shader math
(rotation, per-blade hash, lean, footprint, terrain tilt) and bakes the
procedural blade colours into vertex colours.

- The tufts are capped (default 120000) to keep Blender responsive; when
  exceeded the exporter keeps a deterministic, spatially uniform
  position-hash subset (not a prefix, so no region goes bald). The cap can be
  changed with `BLENDER_EXPORT_MAX_GRASS` before starting the export.
- The instances match the CPU placement path. The default GPU placement
  path produces the same records up to float rounding.
- Wind, impostor hand-off and distance thinning are runtime effects and are not
  exported; blades are static.

## SDF effects

The Vulkan SDF renderer (`SdfRenderer`) owns the CPU-side `sdf_gpu::SdfScene`
that feeds lava flames and smoke. The app passes its definitions,
materials and instances to the exporter; the Blender script creates one proxy
mesh per definition and links one object per instance with the engine transform
(`R = Rx*Ry*Rz`, per-instance height/radius scale) and material (base colour,
roughness, metallic, emission, opacity, texture layer via box projection).

The proxies are approximations: the engine ray-marches the SDFs, so flame
shapes/spikes and smoke density are not reproduced. Flames use a tapered cone;
smoke uses a sphere.

## Limitations

- **Lighting** is not the engine's renderer: a sun (engine light direction and
  colour) plus a flat world colour replace the sky model, cascaded shadow maps,
  cloud shadows and RT reflections. Material *blending* is preserved; absolute
  shading differs.
- **Tessellation displacement** is not applied. The export is the undisplaced
  tessellated surface; the engine applies height-map displacement only when
  runtime tessellation is enabled.
- **Normals**: the engine perturbs normals per projection in world space and
  this is reproduced, but the normal map is applied as a world-space normal;
  materials with `triplanarEnabled == false` go through the same projection
  transform (the engine would use a derivative TBN instead).
- **Mix layers**: the Perlin noise is re-implemented on the CPU, so the pattern
  differs from the GPU-generated texture while the mixing equation, sources
  and parameters match.
- **Ambient occlusion** multiplies the base colour instead of only ambient
  light (Principled BSDF has no AO input).
- **Specular model**: the engine uses Blinn-Phong; the Blender material uses
  Principled GGX with the exponent mapped to roughness. Specular strength is
  mapped to the Specular IOR Level.
- **Water** is a static surface with a simple transmissive material; the
  engine's wave/displacement/reflection shaders are not reproduced.
- **Grass** is capped and static (no wind/impostors), and blades are flat-shaded
  triangles like the engine's base mesh.
- **SDF effects** are proxy meshes, as described above.
- Blender 4.0's importer cannot import integer custom attributes; the packed
  float representation is exact for the values used (< 2^24).

## Validation procedure

Automated (no GPU needed):

```
# 1. headless export from the server scene
cd bin && ./server --export-glb /tmp/octree_export/octree.glb

# 2. import + configure materials, save a .blend and render a test image
cd /tmp/octree_export
blender --background --python-exit-code 1 --python octree_blender.py -- \
    octree.octree.json --engine cycles --samples 16 \
    --save-blend /tmp/octree.blend --render /tmp/octree.png
```

Checks used during development:

- the `.glb` parses with a minimal validator: accessor counts, index ranges,
  `min`/`max` on POSITION, embedded image views;
- >99.5 % of terrain triangles are CCW around their vertex normals (winding
  correction applied);
- the Blender import reports the same triangle count as the glb;
- rendering shows textured terrain, water and (close-up) grass blades;
- a synthetic SDF sidecar (a few flame instances) produces proxy objects
  at the expected world positions.
